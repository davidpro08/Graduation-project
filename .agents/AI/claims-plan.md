계획은 메시지별 명제 추출 → 계약/근거 검증 → 사용자별 DB 저장 → DB 재조회 → 명제 쌍과 원문을 JEV로 분류 → 기존 결과 화면/저장 계약 연결 순서다. 각 경계는 인터페이스·DI·어댑터로 분리한다.

## 구현

- `apps/backend/schemas/message-claims.schema.json`: 사용자 제공 JSON Schema를 보존했다. original_text는 선택 사항이지만 저장 시 서버 원문을 채운다. 빈 claims도 정상 추출로 캐시한다. uncertain은 부정 범위 불명확이며 추측·시간·조건·인용은 qualifiers다.
- QwenClaimHttp: 메시지 하나와 화자/날짜/시간을 넣어 명제를 추출한다. 응답 추가 필드·누락·극성·인용의 원문 포함·ID·원문 일치를 검증한다. 토큰 초과/잘린 출력은 실패하며 원문을 임의로 자르지 않는다.
- message_claims: 메시지별 JSON payload + owner/conversation + source_hash + extractor_version을 저장한다. 메시지/대화/소유자 복합 FK, RLS, 원문 일치 trigger, JSON 구조 CHECK, 삭제 연쇄를 적용한다. 해시는 원문·화자 ID/이름·날짜/시각, 버전은 claims-v1과 모델 ID다. 프롬프트/모델 리비전을 교체하면 추출 버전을 올려야 한다.
- ClaimPipeline: 저장에 성공한 뒤 재조회한 명제만 판단에 쓴다. 같은 입력/버전이면 재사용한다. 추출/저장/재조회/판단이 실패하면 작업을 failed로 끝내고 이미 저장한 명제는 다음 요청에 재사용한다. 기존 Qwen 직접 모순 경로로 자동 우회하지 않는다.
- JEV `/v1/claim-pair`: 명제 두 개와 원문·화자·날짜·시각을 입력한다. contradiction/compatible/unknown의 세 선택지를 평가하고 최대 확률 항목을 반환한다. 동률이면 선언 순서의 첫 항목이다. 출력 순서·확률 합/범위·최대 항목 일치를 검증한다. 기존 페르소나 엔드포인트도 유지한다.
- 결과 metadata에 명제 수, 추출/캐시 메시지 수, 비교 수, 판단 불가 수, 모델, 쌍별 판정/조건부 확률을 기록한다. leftClaim/rightClaim은 이번 실행의 평탄화된 명제 배열 인덱스다. 결과 본문은 서버가 만든 후보 안내와 근거 미리보기이며 JEV가 생성한 설명이 아니다.
- AnalysesService: contradiction만 새 파이프라인으로 보낸다. schedule은 기존 AnalysisRunner/Qwen/날짜 추정/확정 계약을 유지한다. 공개 HTTP 경로·결과 items 계약은 유지한다.

## 범위와 한계

최근 한 달(대화 마지막 날짜 기준)의 텍스트 범위를 유지한다. 그 범위 내 서로 다른 메시지의 모든 명제 쌍을 비교하므로 기존 분할 경계보다 넓게 비교하지만 비용은 제곱으로 증가한다. CLAIM_MAX_PAIRS 기본2000, 허용1~100000을 넘으면 CLAIM_PAIR_LIMIT로 실패한다. 임의 표본만 비교한 뒤 전체 성공으로 표시하지 않는다. 결과1000건 초과는 CLAIM_RESULT_LIMIT다. 동일 메시지 내부 명제끼리는 기존 서로 다른 근거 메시지2개 계약 때문에 비교하지 않는다. 한 메시지의 여러 명제는 각각 다른 메시지 명제와 비교한다.

추출은 메시지 단위이며 앞뒤 대화를 통한 생략 주체·대명사 해소는 아직 없다. 긴 단일 메시지의 토큰 초과는 분할 추출 없이 실패한다. 자동 재시도·부분 판정 복구·명제 추출 진행률·후보 검색 색인은 후속 작업이다. 이미 저장한 명제 캐시 재사용은 지원한다. 원문 인용의 존재 검증은 의미적 타당성/진실을 보장하지 않는다. JEV 확률은 보정된 정확도가 아니며 실제 한국어 모순 데이터 평가가 필요하다. 운영 성능/품질 개선을 검증했다고 주장하지 않는다.
