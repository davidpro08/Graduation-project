1. 이 문서의 현재 상태·마일스톤을 확인하고 사용자 요청의 분야와 변경 경계를 분류한다.
2. 아래 표에서 필요한 문서만 읽는다. 프로젝트 소개가 필요할 때만 [README](../README.md)를 읽는다.
3. 관련 코드·설정만 탐색하여 실제 상태를 확인한다. 문서와 다르면 차이와 근거를 확인하고, 오래된 문서대로 코드를 무조건 바꾸지 않는다.
4. 관련 경계가 바뀔 때 해당 계약·스키마·인프라 문서를 추가로 읽는다. 분야 폴더는 소스 코드 위치가 아닌 컨텍스트 분류다.

## 공통 행동 규칙

- 모든 문서와 답변은 특별한 지시가 없으면 한국어로 작성한다. 핵심을 먼저 간결히 설명한다. 비교·변경·구조화된 데이터는 표로 정리한다.
- 명시적 사용자 지시와 상위 지침을 우선한다. 파일·폴더 이동과 삭제는 특별한 요청 없이 수행하지 않는다. 새 구조는 근거를 설명한다.
- SOLID와 책임 분리를 따른다. 기능 계약에는 인터페이스를 우선하고, 공통 상태·구현과 IS-A 관계가 명확할 때 추상 클래스를 선택한다.
- 새 클래스 전 유사 속성·기능과 책임 과다 여부를 확인한다. 클래스명은 최대 30자로 간결하게 정한다.
- 필요한 디자인 패턴만 적용하고 목적을 결과 보고에 설명한다. 단순 생성에 빌더·팩토리를 추가하거나 편의를 위해 싱글톤을 도입하지 않는다.
- 기술의 사용법·설정·버전을 조사할 때 작업 분야 문서의 공식 링크에서 해당 주제를 먼저 확인한다(frontend: Next.js, backend: NestJS, database: Supabase, infra: AWS). 공식 문서 내용이 부족하면 Context7 MCP로 보완하고 공식 저장소·릴리스 등 1차 출처를 확인한다. 다른 기술은 해당 기술의 공식 문서를 사용한다. 일반 개념·논문·실제 오류 사례·최신 발표는 인터넷의 1차 출처로 조사한다.
- 외부 검색은 영어를 기본으로 하되 한국 자료는 한국어로 찾는다. MCP 오류·반려는 동일 작업에서 최초 시도 포함 최대 3회까지만 시도하고 실패를 보고한다.
- 코드 작성 후 변경에 적합한 검증을 실행한다. 오류 수정·재검증은 최대 3회 수행하며 해결되지 않으면 실패와 남은 문제를 보고한다. 실패를 숨기거나 완료로 표시하지 않는다.
- 비밀 키·토큰·원본 개인 대화는 문서·저장소·로그에 기록하지 않는다. 예시는 합성 데이터를 사용한다.
- 선택된 설계, 구현 완료, 보류를 구분한다. 설치 버전·주소·인스턴스·명령을 추측하여 기록하지 않는다.

## 작업 종료와 문서 갱신

- API 변경은 backend/api.md, AI 계약 변경은 AI/api.md, 데이터 관계 변경은 database/schema.md를 갱신한다. 소비자 영향도 함께 확인한다.
- 라이브러리 추가·제거 시 해당 분야 표에 실제 패키지명·목적·설치 상태·잠금 파일 기준 버전을 기록한다.
- 인프라 변경은 infra/guide.md의 운영 기록을 갱신한다. README에는 전체 구성·기능 변화만 반영한다.
- 중앙 상태에 완료 작업·검증·다음 작업·차단 사항을 갱신한다. 미완료 단계 전체를 완료로 바꾸지 않는다.
- 문서 작업은 링크·대소문자·상태·계약 일관성을 확인한다. 코드 작업은 관련 테스트와 실제 실행 결과를 기록하며, 실행하지 않은 검증은 미실행으로 표시한다.

## 브랜치와 커밋 규칙

- 브랜치는 마일스톤과 기능을 기준으로 `codex/m<번호>/<기능>` 형식으로 나눈다. 기능명은 짧은 영문 소문자와 하이픈을 사용한다. 예: `codex/m0/context-harness`, `codex/m1/turborepo-setup`, `codex/m1/docker-dev`, `codex/m2/conversation-upload`.
- 한 브랜치는 하나의 마일스톤 안에서 일관된 기능을 다룬다. 독립적인 기능은 분리하고, 같은 기능을 완성하는 여러 작은 커밋은 같은 브랜치에 둔다. 기반 작업에 의존하는 브랜치는 기반 병합 후 시작하거나 의존 관계를 명시한다.
- 커밋은 한 작업 단위로 세세하게 나눈다. 예: Git 추적 규칙, workspace 설정, React 초기화, NestJS·Swagger 초기화, Docker 개발 환경, 검증·문서 갱신. 서로 무관한 변경을 한 커밋에 묶지 않는다.
- 커밋 메시지는 `<type>(<scope>): <한국어 작업 요약>` 형식을 사용한다. type은 `feat`, `fix`, `chore`, `docs`, `test`, `refactor` 중 작업에 맞게 고르고 scope는 `repo`, `frontend`, `backend`, `database`, `ai`, `infra` 중 해당 영역을 쓴다.
- 예: `chore(repo): 임시 파일과 의존성 추적 제외`, `chore(repo): pnpm과 Turborepo 작업 구성`, `feat(backend): 상태 확인 API와 Swagger 추가`, `chore(infra): Compose 개발 환경 구성`.
- 작게 나누더라도 필요한 설정·의존성·잠금 파일을 함께 포함해 작업 단위가 재현 가능해야 한다. 기능에 필수인 검증과 계약 수정은 같은 커밋에 포함할 수 있다.
- 커밋 전 `git status --short`와 스테이징 diff를 확인하고 의도한 파일만 경로를 지정해 스테이징한다. unrelated 변경을 포함하는 `git add .`를 기본으로 사용하지 않는다. 해당 작업에 필요한 검증 결과를 확인한다.
- `.agents/`, README, 설정 예제, `pnpm-lock.yaml`은 추적한다. `.tmp/`, node_modules, 빌드·캐시·로그·실제 환경 설정·비밀 키는 `.gitignore`로 제외한다. 로컬 Docker와 호스트 모두에 이 규칙을 적용한다.
- 실제 브랜치·커밋 작업 시 현재 브랜치와 사용자 변경을 먼저 확인한다. 사용자가 지정한 브랜치명은 우선한다. 브랜치 삭제·강제 푸시·기존 커밋 재작성은 별도 지시 없이 수행하지 않는다.

## 사용자 인증 기반 · 2026-10-01

`codex/m2/auth-foundation`에서 Supabase SDK 2.117.2, 사용자 프로필·가입/수정 트리거·RLS·컬럼 권한, Bearer 검증 Guard와 GET/PATCH 내 정보 API를 구현했다. 기존 원격 페르소나 마이그레이션과 신규 사용자 SQL을 로컬에 기록했다. 이메일·제공자는 검증된 Auth 정보에서 읽고 요청별 사용자 토큰으로 DB에 접근한다. 저장소 인터페이스·어댑터·DI로 외부 접근을 분리했다.

백엔드 타입·lint·빌드·통합 테스트 10개, 실제 서버의 health·Swagger·Supabase 잘못된 토큰 401, 원격 DB 가입·정규화·RLS·컬럼 수정 차단·연쇄 삭제 롤백 검증을 통과했다. 테스트 사용자·프로필 잔존 0건과 기존 페르소나 50,000건 유지 확인. 보안 advisor 신규 지적 없음; 기존 페르소나 의도된 무정책 INFO 유지. Compose config 통과, Docker 엔진 미실행으로 컨테이너 검증과 유효 OAuth 로그인 전체 검증은 미실행이다.

관련 계약은 [사용자 API](backend/api.md#사용자-api-계약--2026-10-01), [DB](database/schema.md#사용자-프로필-실제-계약--2026-10-01), [OAuth 준비](infra/guide.md#oauth-연결-준비--2026-10-01)를 참조한다. provider 앱·redirect 설정·프론트 인증·대화 DB는 미구현이며 M2 전체를 완료로 표시하지 않는다. 기존 문서·scripts/ 사용자 변경을 유지했다. 커밋·원격 푸시는 미실행이다.

## ESLint 편집기 파싱 오류 수정 · 2026-10-03

프론트·백엔드 eslint.config.mjs에 tsconfigRootDir을 명시하여 다중 후보 경로 충돌을 해결했다. 두 앱 lint, 한 Node 프로세스에서 양쪽 ESLint 설정 로드·루트 확인·소스 파싱 검증 통과. 런타임·API·DB 변경 없음.

## 참여자 프로필 표시 수정 · 2026-10-03

사용자 요청으로 프로필의 사람 아이콘을 제거하고 이름 앞 두 글자를 중앙에 표시했다. 400개 색상 조합은 배경 20색이 먼저 순환한 다음 글자색이 바뀌도록 계산 순서를 수정했다. 프론트 타입 검사·lint 통과. 공통 프로필 컴포넌트를 재사용하며 추가 디자인 패턴은 도입하지 않았다.

대화 저장·통계 구현을 의존성·DB·백엔드·프론트·문서 5개 로컬 커밋으로 저장했다. 이어서 탭 이동 시 미조회 상태를 `불러오는 중입니다`로 표시하고 실제 API 404만 대화 오류 페이지로 처리했다. 조회 결과를 계정·대화·재조회 요청별로 구분한다. 타입·lint와 정상 탭 이동·없는 대화 오류 화면의 브라우저 검증을 통과했다. 동일 브랜치에 수정 커밋을 추가하며 원격 푸시는 하지 않는다.

## 프론트 OAuth 연결 · 2026-10-03

프론트 하네스를 읽고 기존 로그인 폼을 Google·GitHub·Kakao 공식 리소스 진입점으로 교체했다. SDK 2.117.2 고정 설치, 브라우저 PKCE·단일 코드 교환·Auth Context·내 정보 GET/PATCH·로그아웃·상단 계정 표시·콜백 실패 재확인을 구현했다. 기존 대화 화면의 합성 데이터 체험을 유지하며 실제 대화 저장·분석 연결로 표시하지 않는다. 원격 Auth 제공자·DB 설정은 이번 작업에서 변경하지 않았다.

사용자 명시 요청으로 테스트와 타입·lint·빌드·브라우저·컨테이너 실행을 하지 않았다. [화면 및 수동 확인](frontend/screens.md#oauth-로그인-연결--2026-10-03), [공식 리소스](../apps/frontend/public/auth/README.md), [공개 설정](infra/guide.md#프론트-oauth-공개-설정--2026-10-03)을 참조한다. 로그인 상태는 Context Provider로 공유하고 SDK·API 경계를 화면과 분리했다. 사용자 요청으로 변경 사항을 작업 단위 커밋으로 저장하며 원격 푸시는 하지 않는다.

카카오 로그인은 사용자 성공 보고 및 기존 원격 Auth 로그의 PKCE 200을 확인했다. Google은 invalid_client(Client Secret 불일치), GitHub는 이메일 API 403(Resource not accessible by integration)을 확인했다. 에이전트 로그인 테스트·원격 설정 변경은 하지 않았다. Google·GitHub 수정 후 성공은 미확인이므로 OAuth 전체 완료로 표시하지 않는다. 상세 조치는 [인프라 기록](infra/guide.md#oauth-수동-확인과-오류-조사--2026-10-03)에 저장했다.
